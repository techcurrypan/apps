# 段と完成条件

終わっていない最初の段を進める。**完成条件を全部満たすまで次へ行かない。**
各段の記録は `docs/progress/phase-<N>.md`。完成条件 1 つずつに「どう確かめたか」を書く。

## 順番とその理由

| 段 | 名前 | コード | この位置にある理由 |
|---|---|---|---|
| 1 | 土台と配信 | 書く | 何を作っても、公開して確かめる道が先に要る |
| 2 | 説明の型と検査 | 書く | 中身の基準は画面にもゲームにも依らない。先に固め、見本 1 本で基準そのものを試す |
| 3 | カリキュラム設計 | 書かない | 何を教えるかが決まらないと、ゲームの手も画面も決まらない |
| 4 | ゲーム設計 | 書かない | 学びがどの手になるかは、カリキュラムが決まって初めて書ける |
| 5 | 画面設計 | 書かない | 説明・実戦・ゲームを同じ画面に収めるので、3 と 4 の後 |
| 6 | 画面と再生装置 | 書く | 5 の設計を、見本 1 本で実装する |
| 7 | 道具 | 書く | 3 で決まった実戦が使う物だけを作る |
| 8 | ゲームの実装（港町） | 書く | 4 の設計を街に合わせて直し（8-1）、実装する（8-2）。D-14 |
| 9 | 学びとゲームの接続 | 書く | 6〜8 がそろって初めてつなげる |
| 10 | 本文 | データ | 形が全部決まってから量産する。途中で形が変わると全部直しになる |
| 11 | MCP サーバ | 書く | 本文がそろってから公開する |
| 12 | 通し確認 | 書かない | — |

## 段 1　土台と配信

**目的** push すると検査を通って Workers に出る道を作る。

**作る物**

- この `devlearn/` の中に SvelteKit の雛形（TypeScript / prettier / eslint / vitest /
  adapter-cloudflare）。**既にある `PROMPT.txt` / `CLAUDE.md` / `docs/` は消さない・上書きしない**
- `wrangler.jsonc`。Worker 名 `devlearn`
- `package.json` のスクリプト：`gen` / `check` / `lint` / `test` / `content:check`
  （この段では空で通る）/ `secrets` / `build`
- リポジトリの根の `.github/workflows/deploy-devlearn.yml`（ここから見て `../.github/`）。
  `devlearn/**` の push で動く。作業ディレクトリは `devlearn`。
  `npm ci` → `gen` → `check` → `lint` → `test` → `content:check` → `secrets` → `build` → `wrangler-action`
- 画面 1 枚。配信されたコミットの短い ID と組み立て日時

**完成条件**

1. push で検査が走り、通ると配信される
2. 公開 URL に、今 push したコミットの短い ID が出る
3. わざと型の誤りを入れると検査で止まり、公開 URL は前の版のまま。確かめたら戻す
4. 旧 `swallow` の GitHub Pages が今まで通り動いている
5. 隣の `blog/` の配信が今まで通り動いている（`deploy-blog.yml` を変えていない）
6. Workers 無料枠と課金の条件を `docs/free-services.md` に、確認日と出典つきで書いた

## 段 8　ゲームの実装（港町）

D-14・D-15・D-16 で、舞台は 3D の港町づくり、土台は試作と決まった。8-1 で設計を直し、8-2 で作る。
**読む物**：`docs/city-standard.md`（最重要）、`docs/prototype/README.md`、試作 `docs/prototype/minato.html` とその `src/`。

8-2 は**決まった順（8-2a → 8-2f）**で進める。順を飛ばさない。各手順の終わりに `docs/progress/phase-8.md` に記録してコミットする。

### 8-1　設計の改訂（コードを書かない）

**作る物**

- `docs/game-design.md` に「街」の章を足し、D-14 で置き換える物を書き直す。`game-design-brief.md` 第 6 章の 1〜10 を全て決める
- `docs/screen-design.md` の「仕事場」を「街 `/town`」に書き直す（D-15）
- `docs/decisions.md` に決着として記録

**完成条件**

1. `game-design-brief.md` 第 6 章の 1〜10 が全て `game-design.md` に書かれ、全ての数に根拠がある
2. 段 4 の第 8・9 章（163 本の手、原因と症状）が、そのまま使える形で残っている
3. 学ばない道で一区切りまで通せることを、7.4 と同じく使い捨ての模擬で確かめ、表にした
4. `screen-design.md` の街の章が、`city-standard.md` の画面の項目（S-1〜S-5）を全て含む

### 8-2a　試作をそのまま載せる

- 試作の `src/engine.js`・`gen.js`・`game.js` を `src/lib/city/` に TypeScript として移す。**中身の処理は変えない**。
  変えてよいのは、型を付ける・`any` を無くす・グローバルを関数の引数にする・`#still` の撮影の口を残す、だけ
- 試作の `index.html` の板の配置と見た目を、`/town` の Svelte 部品に移す。文字は `--dl-font`（外の書体を読まない。`screen-design.md` 4.3）、板の色は `--dl-*` のトークン
- 「途中版」の印は外す
- 公開 URL の `/town` と、試作（`file:///` で開いた `docs/prototype/minato.html#still`）を、`city-standard.md` 第 6 章の 5 枚の角度・時刻で撮り、並べて記録する

**終わりの条件** 5 枚の全てで、試作と見た目が同じ（建物・木・車・光・影・板の配置）。違う所があれば直す

### 8-2b　状態の計算を描画から切り離す

- 状態（時刻・資金・人口・満足度・需要・区画・道路・建物・要望・学んだ手）を `src/lib/game/` の純粋な関数（`apply` / `replay`）に移す。
  DOM・WebGL・実時間を知らない
- **一度に 1 つずつ**移し、移すたびに 8-2a の 5 枚を撮り直して、見た目と動きが落ちていないことを確かめる
- 描画（`src/lib/city/`）は、状態を読んで描くだけにする

### 8-2c　本番の仕組みにする

- 要望の解き方を `game-design.md` 第 4〜7 章と 8-1 の街の章どおりにする（候補 4 つ・調べる・示す・直す・いつでもの手）
- 学んだ手は、引数で渡す「修了したレッスンの集まり」で決める（集まりの作り方は段 9）。この段では試験用の集まりで動かす
- 数（費用・収支・人口・満足度・需要・目標）を 8-1 で決めた式にする
- 試作の簡略な解説の画面は使わない。解説は段 9 でレッスンの画面（段 6 の再生装置）につなぐ。この段では「この要望に効くレッスン」の名前と道を出すだけ

### 8-2d　検査を足す

先に失敗するテストを書く。

- 同じ種と同じ手の記録から、2 回流して同じ状態（A-11）
- `src/lib/game/` に `Math.random`・`Date.now`・`performance.now`・`new Date` が無い
- 街の形の生成の結果について：建物の種類が `city-standard.md` V-7 を全て含む／動かない物の三角形が上限内（P-1）／1 枚を描くのに使う形の数が上限内（P-1）
- 学ばない道の決まった遊び方で、一区切りまで通せる（8-1 の表と同じ結果）

### 8-2e　実機で確かめる

- `scripts/look.ts` に街の確かめを足す（手元の Chrome で公開 URL を開く。CI では走らせない）
- 1280×720 の既定のカメラで 10 秒の平均の 1 コマの時間を測り、`city-standard.md` P-5 を満たす。測った値と、手元の機械（CPU・GPU）を記録する
- 390×844（携帯の幅）で、板が重ならず、道具の帯が横に送れ、要望を開いて応えられる
- `city-standard.md` の全項目に ○／× を付けて記録する。× があれば直してから次へ

### 8-2f　利用者の確認で止まる

- 試作と本番を並べた 5 枚と、携帯の幅の 1 枚を `docs/progress/shots/` に置き、`docs/progress/phase-8.md` に並べて載せる
- `docs/decisions.md` の未決に「段 8 の街を見て、良いか直す所を書いてほしい」と書く。
  何を見ればよいか（公開 URL の `/town`、並べた画像の場所）、見る観点（`city-standard.md` の章立て）を書く
- コミットして push し、`DECISIONNEEDED` とだけ出力して終わる
- 次の実行で：利用者が「良い」と書いていれば段 9 へ。直す所が書いてあれば直し、8-2e と 8-2f をやり直す

**段 8 の完成条件**

1. 同じ種で 2 回流して同じ結果
2. 状態を決める処理に `Math.random`・`Date.now`・`performance.now`・`new Date` が無い（テストで確かめる）。
   見た目だけの動き（車・人・船・波・旗）は、種つきの擬似乱数と描画の時刻を使ってよい（`city-standard.md` L-5）
3. 数字が動いたとき「なぜ動いたか」が平易な言葉で出る（資金の内訳・理由の文）
4. 起きた変化を、どうなってどうなったか動きで見せ、繰り返し見返せる（建物が建つ様子をもう一度見られる）
5. 公開 URL の街が `city-standard.md` の全項目を満たす。1 項目ずつ確かめ方と結果を記録した
6. 試作と同じ角度・時刻の 5 枚で、見劣りする項目が無い
7. 手元の Chrome で測った 1 コマの時間が P-5 を満たし、携帯の幅で操作できる
8. **利用者が `decisions.md` に「良い」と書いた**
